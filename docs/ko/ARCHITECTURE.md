# 실제 운영 시스템 구조

이 저장소가 나온 비공개 시스템은 한 사람이 **작은 트레이딩 회사처럼** 운영합니다. 리서치, 주문 실행, 리스크, 감시, 배포, 보고가
각각 자동화된 별도 부분입니다. 그중 실제 운영 모듈 4개를 검사와 함께 [`production/`](../../production)에 공개했고,
나머지는 전략 파라미터(엣지)와 계좌·서버 정보가 들어 있어 비공개로 둡니다.

```
                  ┌──────────────── 리서치 ────────────────┐
 시장 데이터 ────► │ 정본 백테스트  ◄── 설정 파일 하나        │ ── 고정값(숫자가 바뀌면 검사 실패)
 (거래소·브로커·    │ 무작위 대조군 관문 · 기대 금액 · 워크포워드 │ ── 교정 목록 + 아직 못 고친 낙관 목록
  장중 피드)        │ 사전등록 · 기각 장부                     │
                  └──────────────┬──────────────────────────┘
                                 │ 매니페스트(각 전략이 무엇을, 얼마나 거래하나)
                                 ▼
        ┌──────────── 러너: 계좌별·전략별 컨테이너 하나씩 ────────────┐
        │ 신호 → 사이징 → 리스크 가드 → 주문 계획 → 실행 → 결정 저널 │
        └──────┬───────────────────────────────────────┬────────────┘
               ▼                                       ▼
   크립토 거래소 (REST)                       프랍 계좌 (MetaTrader)
   지정가·오프셋 진입, 메이커 우선 청산,        터미널의 EA(MQL5)와 파일로 연동,
   대기 주문 갱신, 남는 현금 → 예치            모든 주문에 전략 꼬리표
               │                                       │
               └──────────────────┬────────────────────┘
                                  ▼
  감시 5겹: 생존 신호 → 상태 점검 → 배포 파일 변조 → 실거래↔백테스트 대조 → 불변식
  보고: 매일 대조 · 매주 신호 재생·실행비용·성과 차이 분해 · 매월 거래소 원본 증빙 보관
  알림: 텔레그램(같은 경보 반복 대신 상태가 바뀔 때만)
```

## 규모

* 메인 서버에 **컨테이너 약 30개**: 계좌별·전략별 러너와 조정기·가드
* **예약 작업 약 40개**: 감시, 보고, 증빙 보관, 예치 스윕, 서버 간 점검
* 방식이 다른 실행처 두 종류: REST로 붙는 크립토 거래소, 직접 만든 EA로 움직이는 프랍 회사 MetaTrader 터미널
* 이 전체를 배포하는 명령 하나, 그리고 통과해야만 배포되는 검사 묶음

## 구성

| 영역 | 하는 일 | 왜 생겼나 (계기가 된 사고) |
|---|---|---|
| **정본 백테스트** | 모든 계좌에 시뮬레이터 하나, 설정은 파일 하나, 대표 숫자 고정 | 새 스크립트를 짤 때마다 교정을 하나씩 빠뜨렸다 ([측정 버그](INCIDENTS.md)) |
| **러너** | 매니페스트 기반: 신호, 사이징, 가드, 주문 계획, 모든 결정을 저널에 기록(진입 또는 건너뜀 + 이유) | 이유를 남기지 않은 건너뜀이 '월요일 봉을 매주 버리는 필터'를 숨기고 있었다 |
| **거래소 실행** | 지정가·오프셋 진입, 메이커 우선 청산(시한 뒤 시장가), 대기 주문 갱신 | 시장가 청산이 가장 큰 비용이었다 ([비용 보고 샘플](../SAMPLE_LIVE_REPORT.md)) |
| **MetaTrader 연동** | 파이썬이 명령을 쓰고 MQL5 EA가 실행. 모든 주문 코멘트에 전략 꼬리표 | 한 전략이 심볼·손절만 보고 다른 전략의 포지션을 자기 것으로 착각한 적이 있다 |
| **리스크 가드** | 하루 손실 가드, 장중 자본 차단기, 낙폭 감축(고점 −10% → 절반), 백테스트 분포 대비 성과 저하 가드, 계좌 간 반대 포지션 가드, 주말·롤오버 처리, 동시 보유·노출 상한 | 각각이 회사 규칙이나 실제로 잰 최악의 날에 대응한다 ([계좌별 규칙](CONSTRAINTS.md)) |
| **대조 감시** | 매일: 실거래가 건너뛴 모든 신호는 백테스트도 아는 이유여야 함. 매주: 백테스트 신호를 실거래 행동과 맞대어 재생 | 수작업 전수조사에서 찾은 불일치의 절반이 실거래만 조용히 건너뛴 것이었다 |
| **실행 보고** | 매주 원본 체결로 실행비용, 매주 전략별 성과 차이 분해 | '슬리피지 vs 가정' 대시보드 칸이 한 번도 채워진 적 없었다 |
| **배포** | 명령 하나: 업로드 → 서버에서 파일 해시 대조 → 바뀐 서비스마다 실제 피드로 주문 없이 1틱 시험 → 해시가 모두 같을 때만 새 기준으로 승인. 커밋 안 된 파일은 거부 | 손으로 복사하다 하루에 여섯 번 승인을 빠뜨렸고, 부분 배포가 승인된 사이징을 조용히 되돌린 적이 있다 |
| **증빙·회계** | 거래소 원본 기록을 월 2회 SHA-256 장부와 함께 보관. 입출금과 기록된 수동 거래를 뺀 시간가중수익률 | 입금으로 늘어난 잔고는 수익이 아니다 |
| **결함 장부** | 결함마다 누가 찾았나(기계·사람)와 얼마나 살아 있었나 | 하루에 결함 두 건을 사람이 경보를 읽다가 찾았다. 기계는 '성공했지만 틀린 동작'을 못 본다 |
